# MySQL设计开发&使用规范

1 规范背景与目的
MySQL数据库与Oracle、SQLServer等数据库相比，其内核优化器有一定的劣势。我们在使用MySQL数据库的时候需要遵循一定规范，扬长避短。设计出适合线上业务的库表。在数据库变更、处理流程、库表设计、SQL编写等方面予以规范，从而为公司业务系统稳定、健康地运行提供保障。
以下场景产生问题不涵盖在SLA内

- 数据库申请了管理员账号
- 数据库中使用了触发器、存储过程、外键、视图、Event
- 表采用了非InnoDB存储引擎
- 因大事务或者慢SQL导致的数据库问题
- 因DDL产生的业务问题

2 数据库设计
以下所有规范会按照【强制】、【建议】两个级别进行标注，遵守优先级从高到低。
对于不满足【强制】级别的设计的，建议业务进行修改。

2.1 库名

1. 【强制】库的名称格式：业务系统名称、业务系统名称_子系统名。
2. 【强制】单实例表个数必须控制在2000个以内（元数据加载缓慢影响数据库性能）
3. 【强制】单表分表个数必须控制在1024个以内（性能不稳定）
4. 【强制】禁止使用触发器、存储过程、外键、视图、Event
5. 【建议】库的名称必须控制在20个字符以内 (开通的程序读写账号和DB名关联，便于排查问题)。

2.2 表结构

1. 【强制】表和列的名称必须控制在40个字符以内，表名只能使用字母、数字和下划线，一律小写。
2. 【强制】创建表时必须显式指定字符集为utf8或utf8mb4。
3. 【强制】创建表时必须显式指定表存储引擎类型，一律为InnoDB。
            a)  因为Innodb表支持事务、行锁、宕机恢复、MVCC等关系型数据库重要特性，为业界使用最多的MySQL存储引擎。而这是其他大多数存储引擎不具备的，因此首推InnoDB
4. 【强制】建表必须有comment
5. 【强制】对于超过100W行或者>2GB的大表进行alter table，必须经过审核，并在业务低峰期执行。          因为alter table会产生表锁，期间阻塞对于该表的一些写入，对于业务可能会产生极大影响。
 a)  默认会走临时表逻辑，但是会对磁盘大量写入产生大量binlog，需要评估磁盘以及下游DTS任务
6. 【强制】禁止使用外键，如果要保证完整性，应由应用程式实现 
7. 建表时关于主键：
            (1)  【强制】强制要求主键为id，类型为int unsigned或bigint unsigned，且为auto_increment
            (2)  【建议】业务主体字段不要使用表的id主键，建议设为其他字段如user_id，order_id等，并建立unique key索引。
            (3)  【建议】比如订单号，可能根据日期生成，如果设为主键，对表会产生大量的随机插入，导致innodb内部page分裂和大量随机I/O，性能下降。这种情况只需使用自增ID做主键即可。
8. 【建议】
          a)  中间表用于保留中间结果集，名称必须以"tmp_"开头。
          b)  备份表用于备份或抓取源表快照，名称必须以"bak_"开头。
          中间表和备份表定期清理。
9. 【建议】同一模块使用的表名要求与模块名强相关，如ota相关采用"ota_" 开头。相关模块的表名与表名之间尽量体现join的关系，如ota_user表和ota_user_login表。
10. 【建议】核心表（如用户表，金钱相关的表）必须有行数据的创建时间字段create_time和最后更新时间字段update_time，便于查问题。
11. 【建议】表中所有字段必须都是NOT NULL属性，业务可以根据需要定义DEFAULT值，若不定义DEFAULT, 需要在业务insert是，给出值即可。
             a)   因为使用NULL值会存在每一行都会占用额外存储空间、数据迁移容易出错、聚合函数计算结果偏差等问题。
12. 【建议】建议对表里的blob、text等大字段，垂直拆分到其他表里，仅在需要读这些对象的时候才去select。

2.3   列数据类型优化

1. 【强制】表中的自增列（auto_increment属性），使用int unsigned / bigint unsigned类型。用int -21亿~+21亿时，业务上考虑会不会溢出。
            因为有符号int存储范围为-2147483648~2147483647（大约21亿左右），溢出后会导致报错。(财务金钱字段除外，可能为负值)
2. 【强制】业务中列值选择性很少的字段，如: status、is_delete字段类型使用tinytint(1)。禁止使用bit 、枚举类型enum、set类型，会导致业务升级、变更不方便。而bit只有程序能识别，导致人为排错困难。
3. 【强制】字符串、文本数据用varchar存储
             因为varchar是变长存储，比定长char更省空间。varchar最多存65535字节，因此在utf8字符集下最多可以存储21844个汉字. 最大varchar(20022)。
             建议：varchar规约varchar(32)、varchar(64)、varchar(255)
4. 【建议】不推荐使用blob，text等类型
            它们都比较浪费硬盘和内存空间。在加载表数据时，会读取大字段到内存里从而浪费内存空间，影响系统性能。确认是否真的需要这么大字段？
            Innodb 变长字段将其超过768字节时，原始page里只会存储20字节的指针或者字段前768字节，该字段余下内容放在overflow-page里。而row模式在compact格式下，原始page和overflow-page都会加载到内存。
5. 【建议】存储金钱的字段，建议用int 单位'分' 比如100元，存储为10000分。
6. 【建议】时间类型尽量选取datetime 、timestamp
            虽然timestamp仅占用4字节，但是范围为1970-01-01 00:00:01到2038-01-01 00:00:00。not null情况下，timestamp必须设置默认值  参考2.7 建表实例。
7. 【建议】使用INT UNSIGNED存储IPv4，不要用char(15)
8. 【建议】使用varchar(20)存储手机号，不要使用整数

2.4   索引设计

1. 【强制】InnoDB表必须主键为id int unsigned/bigint unsigned auto_increment,且主键值禁止被更新。

2. 【强制】主键的名称以"pk_"开头，唯一键以"uniq_"，普通索引以"idx_"开头，一律使用小写格式，以表名/字段的名称或缩写作为后缀。

3. 【强制】InnoDB索引类型必须为BTREE；

4. 【建议】单个表上的索引个数不能超过10个

5. 【建议】在建立索引时，多考虑建立联合索引，并把区分度最高的字段放在最前面。如列userid的区分度可由select count(distinct userid)/count(*)计算出来。

6. 【建议】在多表join的SQL里，保证被驱动表的连接列上有索引，这样join执行效率最高。连接列即where条件后经常用到的列。

7. 【建议】建表或加索引时，保证表里互相不存在冗余索引。对于MySQL来说，如果表里已经存在key(a,b)，则key(a)为冗余索引，需要删除。

8. 【建议】组合索引字段数不建议超过5个

9. 【建议】不建议在频繁更新的字段上建立索引 

2.5   字符集

1. 【强制】数据库：库、表、列所有字符集必须保持一致，为utf8或utf8mb4
2. 【强制】前端程序字符集或者环境变量中的字符集，与数据库、表的字符集必须一致，统一为utf8 . linux服务器默认utf8。window默认gbk，容易乱码
3. 【说明】默认排序集utf8_general_ci, 不区分大小写。为了方便管理，防止程序获取的结果与自己想要的不一致，需要区分大小写的列需要使用程序实现，不能依赖数据库，不建议使用utf8_bin排序集, 二进制存储。
     2.6   java程序端设计建议
4. 【强制】杜绝大事务（>10w行），多采用小事务
5. 【建议】程序连接MySQL或者redis，必须要有连接超时和失败重连机制，且失败重试必须有间隔时间。
6. 【建议】程序报错里尽量能够提示MySQL或redis原生态的报错信息，便于排查错误。
7. 【建议】对于有连接池的程序，必须根据业务需要配置初始、最小、最大连接数，超时时间以及连接回收机制，否则会耗尽数据库连接资源，造成数据库无法响应新连接，造成线上事故。
8. 【建议】对于log或history类型的表，随时间增长容易越来越大，需要按月分表存储 比如: user_login_log_201804、 user_login_log_201805 …. 便于后期对数据清理或归档。
9. 【建议】考虑规避数据库中主从延迟对于业务的影响。从库可能的延迟会对业务造成影响，建议强制一致性的读开启事务走主库（读写分离情况使用），或更新后过一段时间再去读从库。
          start transaction;
          select xxxxx xxx;
          commit;

10. 【建议】多个并发业务逻辑访问同一块数据（innodb表）时，会在数据库端产生行锁甚至表锁导致并发下降，因此建议更新类SQL尽量基于主键去更新。

11. 【建议】业务逻辑之间加锁顺序尽量保持一致，否则会导致死锁。

12. 【建议】对于单表读写比大于10:1的数据行或单个列，可以将热点数据放在缓存里（如mecache或redis），加快访问速度，降低MySQL压力。对可预期的预定/秒杀 临时业务，必须使用队列限制，避免大量连接同时直连MySQL.
      2.7   一个规范的建表语句示例
      一个较为规范的建表语句为：
      CREATE TABLE user (
     `id` bigint(11) unsigned NOT NULL AUTO_INCREMENT comment 'pk_id',
     `user_id` bigint(11) NOT NULL COMMENT '用户id',
     `username` varchar(45) NOT NULL COMMENT '真实姓名',
     `email` varchar(30) NOT NULL COMMENT '用户邮箱',
     `nickname` varchar(45) NOT NULL COMMENT '昵称',
     `avatar` int(11) NOT NULL COMMENT '头像',
     `birthday` date NOT NULL COMMENT '生日',
     `sex` tinyint(4) DEFAULT '0' COMMENT '性别',
     `short_introduce` varchar(150) NOT NULL COMMENT '一句话介绍自己，最多50个汉字',
     `user_resume` varchar(300) NOT NULL COMMENT '用户提交的简历存放地址',
     `user_register_ip` int NOT NULL COMMENT '用户注册时的源ip',
     `create_time` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '用户记录创建的时间',
     `update_time` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '用户资料修改的时间',
     `user_review_status` tinyint(1) NOT NULL COMMENT '用户资料审核状态，1为通过，2为审核中，3为未通过，4为还未提交审核',
     PRIMARY KEY pk_id (`id`),
     UNIQUE KEY `uniq_user_id` (`user_id`),
     KEY `idx_username`(`username`),
     KEY `idx_create_time`(`create_time`,`user_review_status`)
      ) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='网站用户基本信息';

3  SQL编写规范
3.1 DML语句

1. 【强制】SELECT语句必须指定具体字段名称，禁止写成"*"
          因为select *会将不该读的数据也从MySQL里读出来，造成网卡压力。且表字段一旦增减，但java 映射代码/ model层没有来得及更新的话，系统会报错。

2. 【强制】insert语句指定具体字段名称，不要写成insert into t1 values(…)，道理同上。

3. 【强制】事务涉及的表必须全部是innodb表。否则一旦失败不会全部回滚，且易造成主从库同步中断。

4. 【强制】生产数据库中强烈不推荐大表上发生全表扫描，但对于100行以下的静态表可以全表扫描。查询数据量不要超过表行数的25%，否则不会利用索引。

5. 【强制】WHERE 子句中禁止只使用全模糊的LIKE条件进行查找，必须有其他等值或范围查询条件。

6. 【强制】生产环境禁止使用hint，如sql_no_cache，force index，ignore key，straight join等。
          因为hint是用来强制SQL按照某个执行计划来执行，但随着数据量变化我们无法保证自己当初的预判是正确的，选择让MySQL优化器自行判断！

7. 【强制】where条件里等号左右字段类型必须一致，有可能无法利用索引。

8. 【强制】SELECT|UPDATE|DELETE|REPLACE要有WHERE子句，且WHERE子句的条件必需使用索引查找。

9. 【强制】索引列不要使用函数或表达式，否则无法利用索引。如where length(name)='Admin'或where user_id+2=10023。

10. 【建议】insert into…values(XX),(XX),(XX).. 这里XX的值不要超过5000个。
               值过多虽然上线很快，但会引起主从同步延迟。

11. 【建议】in值列表限制在500以内。
               例如select… where userid in(….500个以内…)，这么做是为了减少底层扫描，减轻数据库压力从而加速查询。

12. 【建议】事务里批量更新数据需要控制行数量，进行必要的sleep，做到少量多次。

13. 【建议】分页查询，当limit起点较高时，可先用过滤条件进行过滤。
                   如select a,b,c from t1 limit 10000,20;优化为:    Select a,b,c from t1 where id>10000 limit 20;

3.2   多表连接

1. 【强制】禁止跨db的join语句。因为这样可以减少模块间耦合，为数据库拆分奠定坚实基础。
2. 【强制】禁止在业务的更新类SQL语句中使用join，比如update t1 join t2…
3. 【建议】不建议使用子查询，建议将子查询SQL拆开结合程序多次查询，或使用join来代替子查询。
4. 【建议】线上环境，同DB多表join不要超过3个表。
5. 【建议】多表连接查询推荐使用别名，且SELECT列表中要用别名引用字段，数据库.表格式，如"select a from db1.table1 alias1 where …"
6. 【建议】在多表join中，尽量选取结果集较小的表作为驱动表，来join其他表。

3.3 事务

1. 【建议】事务中INSERT|UPDATE|DELETE|REPLACE语句操作的行数控制在2000以内，以及WHERE子句中IN列表的传参个数控制在500以内。
2. 【建议】批量操作数据时(如定期的Job)，需要控制事务处理间隔时间，进行必要的sleep，一般建议值5-10秒。
3. 【建议】对于有auto_increment属性字段的表的插入操作，并发需要控制在200以内。
4. 【建议】事务里包含SQL不超过5个（支付业务除外，支付慢用户都能忍）
          因为过长的事务会导致锁数据较久，MySQL内部缓存、连接消耗过多等雪崩问题。
5. 【建议】事务里更新语句尽量基于主键或unique key，如update … where id=XX;
          否则会产生间隙锁，内部扩大锁定范围，导致系统性能下降，产生死锁。
6. 【建议】尽量把一些典型外部调用移出事务，如调用webservice，访问文件存储等，从而避免事务过长。
7. 【建议】对于MySQL主从延迟严格敏感的select语句，请开启事务强制访问主库。

3.4 排序和分组

1. 【建议】减少使用order by，和业务沟通能不排序就不排序，或将排序放到程序端去做。Order by、group by、distinct这些语句较为耗费CPU，很容易造成数据库的CPU飙升。
2. 【建议】order by、group by、distinct这些SQL尽量利用索引直接检索出排序好的数据。如where a < 10 order by可以利用key(a,b)。
3. 【建议】包含了order by、group by、distinct这些查询的语句，where条件过滤出来的结果集请保持在1000行以内（结果集越小，排序越快），否则SQL会很慢。

3.5 线上禁止使用的SQL语句

1. 【强制】禁用update|delete t1 … where a=XX limit XX; 这种带limit的更新语句。
          因为会导致主从不一致，导致数据错乱。建议加上order by PK
2. 【强制】禁止使用关联子查询，如update t1 set … where name in(select name from user where…);效率极其低下。
3. 【强制】禁用procedure、function、trigger、views、event、外键约束。
          因为他们消耗数据库资源，降低数据库集群可扩展性。推荐都在程序端实现。
4. 【建议】禁用insert into …on duplicate key update…
          在高并发环境下，会造成主从不一致。
5. 【建议】禁止联表更新语句，如update t1,t2 set xxx where t1.id=t2.id…

4 安全规范
【必须】日志记录需保存180天以上
【必须】数据库账号密码禁止明文硬编码在代码中
【必须】生产数据不得导入测试环境使用（preprod可以算prod环境）
【必须】禁止从非生产访问生产环境库
【必须】生产数据导出需提交审批流，不可通过非正常技术手段导出
【建议】L2级以上数据在数据库存储应进行字段加密
【建议】防范SQL注入

使用预编译语句：在应用程序中使用参数化查询或预编译语句，避免SQL注入攻击。
输入验证：对所有用户输入进行验证和清理，确保其不包含恶意代码。
